## 1. Цель испытаний

1.1 Настоящий тест-план устанавливает цели, объект, объём, методы, средства, порядок, критерии приёмки и регламент фиксации дефектов при испытаниях информационной системы (далее — ИС) «Заречное», разработанной в рамках курсового проекта по варианту 11.

1.2 Целью испытаний является проверка соответствия ИС «Заречное» требованиям технического задания (далее — ТЗ) и подтверждение готовности системы к приёмке, в том числе:

а) корректности и полноты структуры базы данных (56 таблиц, 12 доменов, 93 внешних ключа, 7 представлений, 6 триггеров, 12 хранимых процедур/функций);

б) корректности загруженного демо-набора данных (100 голов, 5 групп, 8 пастбищных участков, ~9,3 тыс. задач, ~29,7 тыс. движений склада за 2 года истории);

в) работоспособности REST API на платформе Node.js 22 + Express, реализованного в объёме недель 1–5 и расширенного в неделю 6;

г) соблюдения бизнес-правил предметной области на стороне сервера и СУБД (атомарность складских операций, регламент статусов животных, нормы выпаса, withdrawal-периоды, шаблоны задач, закрытие периода);

д) реализации ролевой модели доступа (RBAC), аутентификации, аудита и разделения бизнес- и технического контуров администрирования;

е) устойчивости к некорректным входным данным, отказам СУБД и нагрузке.

1.3 Испытания проводятся для следующих групп требований: функциональные, интеграционные, нагрузочные, безопасности, юзабилити, отказоустойчивости и автоматизации (раздел 6).

1.4 Результатом испытаний является протокол испытаний с отметкой «принято / не принято» по каждому тест-кейсу раздела 8 и итоговое решение о соответствии ИС критериям приёмки раздела 7.

## 5. Методы испытаний

5.1 Применяются следующие методы:

а) **Статический анализ** — просмотр исходного кода, схемы БД, OpenAPI-спецификации и документации на предмет полноты маршрутов, наличия `withTransaction` во всех write-путях, отсутствия `password_hash` / `token_hash` в ответах API.

б) **Динамическое тестирование «чёрного ящика»** — HTTP-запросы к REST API с проверкой кода состояния, тела ответа и побочных эффектов в БД.

в) **Структурные ассерты БД** — SQL-запросы к `information_schema` и представлениям (CHECK 1–2 в `99_checks.sql`).

г) **Позитивные тесты** — корректные входные данные, ожидаемый результат (создание, изменение, выполнение операции, расчёт).

д) **Негативные тесты** — некорректные, отсутствующие, конфликтующие и запрещённые данные; ожидается 400 / 401 / 403 / 404 / 409 / 423 / 428 / 503 и **отсутствие частичных изменений** в БД.

е) **Тестирование граничных значений и классов эквивалентности** — `limit` (1, 50, 200, 201), `qty` (0, 0.000001, сверх остатка), даты (сегодня, будущее, 30/31 день горизонта), длина `X-Override-Reason` (0, 500, 501).

ж) **Проверка транзакционной атомарности** — намеренный вызов ошибки внутри write-операции и последующая сверка состояния БД (откат «полусписанного» корма, отсутствие осиротевших записей).

з) **Матричный метод RBAC** — 6 ролей × группы прав; для каждой пары «роль → маршрут» проверяется разрешённый или запрещённый доступ и запись `DENY`.

и) **Трассируемость** — сопоставление каждого пункта ТЗ с тест-кейсами (таблица 8.1).

к) **Контрольные расчёты** — сверка `v_stock_balance_check` (`balance_qty = calc_qty`), площади `area_ha` по `ST_Area`, FCR и расхода корма при закрытии периода.

л) **Инжекция отказов** — остановка контейнера `farm_pg`, недоступность порта, невалидный JSON, повторное выполнение операции (идемпотентность).

м) **Нагрузочное тестирование** — серии параллельных GET/POST-запросов с замером времени отклика и доли ошибок.

5.2 Для каждого тест-кейса фиксируются: идентификатор, предусловия, входные данные, шаги, ожидаемый результат, фактический результат, отметка «пройден / не пройден», ссылка на дефект (при наличии).

## 10. Регламент фиксации дефектов

10.1 Дефектом считается любое расхождение фактического результата тест-кейса с ожидаемым (таблицы 8.1, 8.2), а также невыполнение критерия раздела 7.

10.2 Форма карточки дефекта (таблица 10.1).

**Таблица 10.1 — Поля карточки дефекта**

| Поле | Содержание |
|---|---|
| ID | `BUG-NNN` (сквозная нумерация) |
| Дата / время | ДД.ММ.ГГГГ ЧЧ:ММ (MSK) |
| Автор | ФИО тестировщика / роль |
| Конфигурация | C1…C6 по таблице 9.2, версии ПО |
| ID тест-кейса | TC-… по таблице 8.2 |
| Пункт ТЗ | ссылка на таблицу 3.1 |
| Компонент | БД / маршрут / middleware / документация |
| Краткое описание | одно предложение |
| Шаги воспроизведения | нумерованный список, с точными телом запроса и учётной записью |
| Фактический результат | код HTTP, тело ответа, состояние БД |
| Ожидаемый результат | по таблице 8.2 |
| Серьёзность | S1…S4 по таблице 10.2 |
| Приоритет | P1…P4 |
| Вложения | лог сервера, вывод `psql` / smoke, скриншот, SQL-снимок |
| Статус | Новый → Назначен → В работе → Исправлен → Проверка → Закрыт / Отклонён |
| Связи | дубликаты, регрессионные TC |

10.3 Классификация серьёзности (таблица 10.2).

**Таблица 10.2 — Серьёзность дефектов**

| Код | Категория | Пример | Срок устранения | Влияние на приёмку |
|---|---|---|---|---|
| S1 | Критический | не загружается схема; обход RBAC; потеря/порча данных; отрицательный остаток прошёл | немедленно | блокирует |
| S2 | Серьёзный | неверный код HTTP, отсутствие отката транзакции, нет записи `DENY`, не работает `/admin/*` или `/tech/*` | до повторного прогона | блокирует |
| S3 | Средний | неверный текст ошибки, расхождение OpenAPI и кода, пагинация, отсутствие `total` | до защиты | не блокирует при согласовании |
| S4 | Незначительный | опечатка в документации, форматирование | по возможности | не блокирует |

10.4 Порядок работы с дефектами:

10.4.1 Обнаруженный дефект регистрируется немедленно, до изменения стенда; стенд «замораживается» до снятия логов.

10.4.2 Для S1/S2 испытания приостанавливаются; после исправления выполняется **полный** повтор п. 4.2.1–4.2.9 (регрессионный прогон), а не только упавший тест-кейс.

10.4.3 Для S3/S4 допускается выборочный повтор затронутых TC-кейсов с обязательным повтором `99_checks.sql` и `smoke_api.py`.

10.4.4 Повторное открытие (Reopen) допускается, если дефект воспроизведён на той же конфигурации после статуса «Исправлен».

10.4.5 Дефект «Отклонён» оформляется только с обоснованием (неверные предусловия, отклонение от ТЗ в шагах, особенность демо-данных).

10.4.6 Итоговый протокол содержит сводку: всего TC, пройдено, не пройдено, заблокировано, число дефектов по S1–S4, перечень открытых дефектов, решение о приёмке по разделу 7.

10.5 Ответственные: тестировщик — регистрация и проверка; разработчик — исправление; руководитель курсового проекта — решение о допуске S3/S4 и утверждение протокола.
