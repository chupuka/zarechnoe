# Продукт: ИС «Заречное»

**Что это:** учёт фермерского хозяйства (~75 га, КРС) — единая система для реестров животных, групп, осмотров, вакцинаций, склада, участков, выпаса, перемещений, задач, сотрудников, аналитики и административных функций. Фронтенд — статическое приложение на vanilla HTML/CSS/JS (`ui/public/`), разворачивается на GitHub Pages; данные и отчёты — через REST API и сервис отчётов.

**Для кого:** владелец/директор, ветврач, бригадир, завхоз, администратор БД, суперпользователь. У каждого своя роль, свой набор прав (RBAC-меню строится из `permissions`), свои сценарии. Автологина нет — вход через форму; демо-логины: `director`, `vet`, `foreman`, `storekeeper`, `dba`, `superuser`, пароль `demo1234`.

**Тон текстов:** деловой, конкретный, без маркетинга. Никаких «суперчардж», «мирового класса», «невероятных возможностей». Ошибка объясняет, что случилось и что делать. Подписи — sentence case; капс допустим только для коротких мета-подписей (группы меню, `thead`, KPI-подписи).

## Роли и ключевые вопросы интерфейса

### Директор (`director`)
1. Кабинет: «Сколько животных и в каком состоянии? Что требует внимания сегодня?» — KPI, donut стада, карта пастбищ, задачи в работе.
2. Аналитика: «Какая себестоимость и FCR по периодам? Где перегруз пастбищ?» — отчёты и графики.

### Ветврач (`vet`)
1. Реестр здоровья: «Кто на лечении, у кого просрочен осмотр или вакцинация?»
2. Карточка животного: «Какие осмотры и прививки сделаны, что запланировано дальше?»

### Бригадир (`foreman`)
1. Выпас: «Какая группа на каком участке и где находится стадо на карте?»
2. Задачи: «Что в работе, что просрочено, кто ответственный?»

### Завхоз (`storekeeper`)
1. Склад: «Какие остатки и сроки годности? Что заканчивается?»
2. Движения: «Кто и когда списал/получил позицию, по какому документу?»

### Администратор БД (`dba`)
1. Безопасность: «Есть ли отказы доступа, подозрительные операции, актуальны ли бэкапы?»
2. Техническое состояние: «Какой размер БД, скорость запросов, не накопились ли ошибки?»

### Суперпользователь (`superuser`)
1. Администрирование: «Кто есть в системе, какие роли и разрешения, кто заблокирован?»
2. Контроль: «Что изменилось в журнале аудита и почему?»

### Техническая роль (X-Override-Reason)
При действиях от имени технической роли модалка запрашивает причину — заголовок `X-Override-Reason`. Поле обязательно, значение пишется в журнал аудита. Не удалять и не обходить.

## Ключевые сценарии (общие)

1. **Вход:** логин/пароль → RBAC-меню → стартовый раздел роли (настраивается в «Моих настройках»).
2. **Поиск действия:** `Ctrl+K` → поиск → выбор операции или раздела → hotkey `N/E/B/R` для частых действий.
3. **Работа с реестром:** фильтры → сохранённый набор фильтров → сортировка → пагинация → строка → редактирование.
4. **Создание:** FAB или `N` → палитра действий → модалка → валидация → сохранение.
5. **Карта:** участки и контуры пастбищ, popup со статусом; в тёмной теме тайлы затемняются.
6. **Отчёт:** выбор периода → donut/bars/KPI → перерисовка при смене темы.
7. **Справка:** `?` — справка по ролям и горячим клавишам; демо-сценарий для преподавателя доступен из меню.
8. **Выход:** возврат к экрану входа, сессия очищается.

## DEMO-границы

Демо предназначено для показа и обучения. **Не выполнять** разрушающие операции: восстановление бэкапов, apply/rollback миграций, удаления, блокировки. Проверка — преимущественно чтение; создание/редактирование — только на демо-записях. Это ограничение сценария, а не бизнес-логики.
