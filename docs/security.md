# Механизмы защиты и администрирование

> ИС «Заречное» (Вариант 11), Неделя 6. Глава для специальной части ПЗ
> (в отдельный Word-документ ПЗ пока не переносится — по договорённости).

## 1. Модель угроз и принципы

| Принцип | Реализация |
|---|---|
| Разграничение доступа | RBAC «Роль × Объект × Действие», проверка на сервере на каждый запрос |
| Минимальные привилегии | 6 фиксированных ролей; технические роли не имеют сотрудника и не участвуют в бизнес-процессах |
| Защита «от клиента» | Никаких проверок только на UI: все бизнес-правила — в API и хранимых процедурах |
| Подотчётность | `audit_log` (бизнес-аудит) + `tech_log` (тех. контур) + `DENY` на каждый отказ |
| Целостность | CHECK / FK / триггеры / транзакции с откатом |
| Конфиденциальность | bcrypt-пароли, sha256-хэши токенов, санитизация ввода, параметризованные запросы |

## 2. Матрица ролей (RBAC, 42 права)

| Роль | Тип | Ключевые права | Ограничение |
|---|---|---|---|
| `DIRECTOR` Директор | BUSINESS | `period:EXEC`, `user:*`, `settings:*`, `audit:READ`, `catalog:*`, `employee:*`, `backup:READ`, `report:READ` | Не пишет в реестры животных/склада; бэкапы — только просмотр |
| `SUPERUSER` Суперпользователь | TECHNICAL | Все 42 права, включая `tech:*`, `backup:EXEC` | Нет `employee_id` → `fn_require_user` блокирует участие в кормлении/выпасе; каждое действие — с `X-Override-Reason` |
| `DBA` Администратор БД | TECHNICAL | `tech:*`, `backup:READ/EXEC`, `audit:READ`, `settings:READ`, `user:READ`, `catalog:READ`, `employee:READ`, `report:READ` | **Только чтение** справочников и персонала; нет записи в бизнес-реестры |
| `VET` Зоотехник/ветеринар | BUSINESS | `animal:WRITE`, `health:*`, `disposal:*`, `ration:*`, `catalog:READ`, `employee:READ` | Нет `user:*`, `tech:*` |
| `FOREMAN` Бригадир | BUSINESS | `stock:WRITE`, `pasture:*`, `task:*`, `employee:READ` | Нет `stock:DELETE` (списание — только кладовщик) |
| `STOREKEEPER` Кладовщик | BUSINESS | `stock:*`, `purchase:*`, `catalog:READ`, `employee:READ` | Нет доступа к животным и задачам на запись |

Неделя 6 выделила собственные права:
`catalog:READ/WRITE`, `employee:READ/WRITE`, `backup:READ/EXEC`.
Ранее справочники использовали права доменов (`group:*`, `stock:*`, `user:*`),
что позволяло, например, кладовщику менять единицы измерения «заодно» с приходом.
Теперь изменение справочников — отдельная привилегия.

## 3. Аутентификация

- Пароли: **bcrypt** (`bcryptjs`, 10 раундов), в `app_user.password_hash` только хэш.
  Сложность: ≥ 8 символов, ≥ 1 заглавной, ≥ 1 цифры (проверяется API).
- Сессии: случайный токен `crypto.randomBytes(32)`, в `user_session` хранится
  **только sha256-хэш**; TTL 8 ч; `logout` отзывает сессию (`revoked_at`).
- Блокировка: 5 неудачных попыток → `locked_until = now() + 15 мин` (HTTP 423),
  счётчик сбрасывается при успехе; разблокировка — `POST /admin/users/:id/unlock`.
- При удалении пользователя все его сессии отзываются **в той же транзакции**.
- `authenticate` на каждый запрос перечитывает права из `role_permission` —
  смена роли действует сразу, без перевыпуска токена.

## 4. Авторизация

`middleware/rbac.js` → `requirePermission(code, entity)`:
- нет права → **403** + запись `audit_log(action='DENY')` с путём и требуемым правом;
- конфиденциальные операции (списание) проверяют второе право внутри роута;
- `elevated(code, entity)` = `requirePermission` + `requireOverrideReason` —
  для действий технических ролей.

### Усиленный аудит технических ролей

`middleware/elevated.js`: у `req.user.role.type === 'TECHNICAL'` требуется заголовок
`X-Override-Reason` (≤ 500 символов). Без него — **428 Precondition Required**.
`req.audit = { isElevated: true, reason }`, и `writeAudit()` автоматически пишет
`is_elevated = TRUE`, `override_reason = <причина>` в `audit_log`.
Страховка на уровне БД: `CHECK (NOT is_elevated OR override_reason IS NOT NULL)`.

## 5. Аудит и логи

| Журнал | Содержимое | Доступ |
|---|---|---|
| `audit_log` | кто/когда/что (до/после JSON)/IP/UA/`DENY`/`OVERRIDE`/`is_elevated` | `audit:READ`, CSV-экспорт по `export:EXEC` |
| `tech_log` | миграции, бэкапы, restore, VACUUM/REINDEX | `tech:READ` |
| `user_session` | выдача/отзыв/истечение токенов | `user:READ` |
| `notification` | уведомления (LOW_STOCK, VACCINE_OVERDUE, …) | только владелец |

Журналы физически разделены: бизнес-админка (`/admin/*`) не показывает `tech_log`,
технадминка (`/tech/*`) не показывает реестры пользователей.

## 6. Защита от типовых атак

| Угроза | Мера |
|---|---|
| SQL-инъекция | Только параметризованные `$1..$n`; `sort`/поля — по whitelist (`Set`), `execFile` без shell в бэкапах |
| Массовое присвоение | `validate()` отбрасывает неизвестные поля, `reject` для `status`/`is_deleted`/`password_hash` |
| Эскалация прав | Права читаются из БД, не из тела запроса; смена роли → `X-Override-Reason` + аудит |
| Перебор пароля | bcrypt + блокировка после 5 попыток + аудит `LOGIN` |
| Кража токена | В БД только sha256-хэш, TTL, отзыв при удалении пользователя |
| Обход бизнес-правил | Триггеры и хранимые процедуры (withdrawal, отдых участка, запрет минуса) |
| Частичные изменения | `withTransaction` + `FOR UPDATE` + ROLLBACK при любой ошибке |
| XSS (UI) | Экранирование вывода, `textContent` вместо `innerHTML` для данных |

## 7. Администрирование

**Бизнес-админка** `/api/v1/admin/*`: пользователи (CRUD, смена пароля, unlock,
мягкое удаление + отзыв сессий), роли, каталог прав, настройки хозяйства,
журнал аудита + CSV, активные сессии, уведомления.

**Технадминка** `/api/v1/tech/*`: резервные копии, восстановления, технический лог,
метрики БД, обслуживание (VACUUM/ANALYZE/REINDEX). См. [backup_policy.md](backup_policy.md).
